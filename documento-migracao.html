Migração dos sites do Liferay para Strapi + Next.js

O que foi feito para tirar os 11 sites públicos do Liferay mantendo o visual idêntico, como a nova stack funciona, como validar e o que ainda falta.

1. Resumo 2. Contexto e decisões 3. Arquitetura 4. Modelo de conteúdo no Strapi 5. Como o front monta a página 6. Widgets e APIs do front 7. Processo de migração 8. Validação visual 9. Como rodar e testar 10. Pendências e riscos 11. Próximos passos

1. Resumo

Os 11 sites públicos que hoje rodam no Liferay DXP foram migrados para uma stack sem Liferay: o conteúdo fica no Strapi e os sites são servidos por um front em Next.js. O Liferay de produção é usado apenas como fonte, uma vez, pelas ferramentas de migração; nada dele roda na stack nova.

A fidelidade visual é medida automaticamente, página por página, comparando screenshots do site atual com o novo em desktop e celular. No piloto (NotreDame) a diferença média ficou em 0,47% dos pixels; nos sites maiores a comparação completa está em andamento (seção 8).

2. Contexto e decisões

  • Prazo: a Hapvida não vai renovar o Liferay e deu um mês para migrar tudo.
  • Critério de aceite: os sites precisam ficar visualmente idênticos. Reaproveitamento de código, segurança e experiência do editor de marketing não eram prioridade nesta fase.
  • CMS: Strapi 5 (definido pela Hapvida; uma primeira versão em Payload foi descartada).
  • Sem Liferay na stack: uma primeira abordagem gravava o HTML renderizado pelo Liferay e o servia de novo (um "espelho"). Visualmente funcionava, mas continuava sendo o Liferay (runtime, rotas /o/..., JS do portal) e foi descartada. A versão atual reconstrói cada página a partir de conteúdo estruturado no Strapi.
  • Hospedagem: por enquanto tudo sobe com Docker Compose; HML e produção vão para Azure.
  • Área logada: são links para outros sistemas; foram mantidos como links.
  • Cookies: OneTrust, mantido como script na página.

4. Modelo de conteúdo no Strapi

TipoO que guarda
SiteDomínio, chave, código, arquivos do tema, estilos globais, scripts de terceiros (OneTrust, analytics), configurações (ex.: chave do Google Maps)
Master pageEsqueleto comum (cabeçalho, rodapé) com os fragmentos e widgets dele
PáginaURL calculada (slug + página pai), SEO, esqueleto, CSS da página, arquivos do tema, fragmentos e widgets
Modelo de fragmentoHTML do bloco com marcadores {{c:campo}} e {{a:campo:atributo}}, mais o CSS e o JS do bloco
RedirecionamentoEndereço antigo → novo, com status 301/302
Estrutura / ConteúdoArtigos, notícias, banners e cards (os antigos web contents), com campos, categorias e datas
obj-* (16 tipos)Dados que os widgets usam: unidades, especialidades, notícias, FAQ, informações regulatórias, demonstrativos, planos... Gerados automaticamente a partir das definições dos Objects
Vocabulário / CategoriaTaxonomia (temas, anos, tipos de unidade, locais...), na ordem original
Envio de formulárioTudo que os formulários dos sites enviam (leads, ouvidoria, contato, Salesforce, e-mail)

Cada página guarda um esqueleto (o layout: seções, linhas, colunas) com marcadores onde entram os fragmentos. Cada fragmento é uma instância de um modelo com os textos, imagens e links daquela página como campos editáveis. O editor altera um texto ou uma imagem no Strapi, publica, e o site muda.

5. Como o front monta a página

  1. O front identifica o site pelo domínio da requisição e chama GET /api/renderizar?dominio=&caminho= no Strapi.
  2. Recebe site, master, página e os modelos usados, e monta o HTML: master → esqueleto da página → fragmentos preenchidos com os campos → widgets.
  3. No <head> entram o CSS do tema da página, os estilos globais do site, o CSS da página e o de cada modelo, os scripts de terceiros e o SEO.
  4. O JS de cada fragmento roda com o mesmo contrato de antes (fragmentElement, configuration), então o código existente dos blocos funciona sem reescrita.
  5. Os ganchos que o JS dos temas usava do portal (AUI().ready, Liferay.on, themeDisplay) são atendidos por um objeto próprio do front, Pagina, e por window.__SITE__.
  6. As mídias são servidas em /midia/..., no domínio do próprio site.

6. Widgets e APIs do front

Os 18 widgets React do repositório (unidades, notícias, blog, filtros, FAQ, acesso por perfil, planos, formulário de landing page...) foram copiados para front/widgets/ com os mesmos componentes e o mesmo CSS. Só a camada de dados foi reescrita para usar as APIs do próprio front:

RotaSubstitui
/api/objetos/<objeto>Consulta aos Objects, com filtro, busca, ordenação, paginação e relações
/api/conteudos/estruturas/<id>Conteúdos estruturados (artigos, notícias), incluindo ordenação por campo
/api/taxonomia/...Vocabulários e categorias
/api/unidades/filtros, /api/unidades/chave-mapaServiço Java de filtros de unidades e a chave do Google Maps
/api/formularios/<nome>Formulários de portlet (ouvidoria) e o lead da landing page
/api/servicos/<serviço>/<ação>Serviços chamados pelos formulários: e-mail, Salesforce, fale conosco, lista dinâmica, corretor, estados e cidades

Portlets que o Liferay já entregava renderizados (Asset Publisher, Web Content, menus, breadcrumb, portlets Java da Hapvida) foram migrados com o HTML que produziam, junto com o CSS e o JS dos módulos da Hapvida.

7. Processo de migração

Tudo é automatizado e pode ser repetido (o processo é idempotente):

migracao/migrar-todos.sh                 # todos os sites + objetos, conteúdos e taxonomia
migracao/migrar-todos.sh hapvida minas   # só esses sites
SEM_EXTRAIR=1 migracao/migrar-todos.sh   # reimporta sem extrair de novo
EtapaScriptO que faz
Extraçãoextrair.mjsLê o HTML público de cada página; separa master e conteúdo; transforma cada fragmento em modelo + campos; descarta o runtime do portal; baixa CSS, JS e imagens dos temas e módulos
Importaçãoimportar.mjsGrava site, masters, páginas, modelos e redirecionamentos; sobe as mídias
DadosgerarTipos.mjs, importarObjetos.mjsCria os tipos obj-* e importa os registros dos Objects
ConteúdosimportarConteudos.mjsArtigos, notícias, banners e cards, com imagens
TaxonomiaimportarTaxonomia.mjsVocabulários e categorias citados nos dados, na ordem original
Validaçãocomparar.mjsScreenshots do site atual × novo e % de pixels diferentes

O que o extrator troca para não depender do Liferay

  • Links e mídias apontam para o site novo; links entre sites usam o domínio cadastrado.
  • Atributos dos campos editáveis ganham nomes neutros (data-campo), e o CSS e o JS que dependiam deles são ajustados junto.
  • Ganchos do portal no JS (AUI().ready, AUI().one, Liferay.on, themeDisplay) viram o objeto Pagina, jQuery e dados do site.
  • Formulários de portlet e chamadas a serviços /o/... passam a enviar para as APIs do front.
  • Loader, combos, SPA e demais scripts internos do portal são descartados. O extrator avisa se descartar algum script que pareça código da Hapvida; hoje nenhum é descartado.

8. Validação visual

Para cada página, o comparador abre o site atual e o novo em desktop (1440 × 900) e em celular (iPhone 13), congela animações, controla o relógio da página (para carrosséis com timer ficarem no mesmo ponto) e mede a porcentagem de pixels diferentes. O relatório de cada site fica em migracao/relatorio-visual/<site>/index.html, com as imagens lado a lado.

As diferenças restantes estão sendo tratadas por causa, não por página. As causas já resolvidas (temas misturados, CSS associado ao fragmento errado, JS de tema dependente do portal, CSS de CDN, imagens de tema, um bug antigo de widget) corrigem dezenas de páginas de uma vez.

Diferenças que não são da migração e aparecem no ambiente local:

  • O banner de cookies e o aviso de privacidade do OneTrust só funcionam nos domínios autorizados; em localhost não aparecem.
  • Arquivos que dão 404 no próprio site atual continuam faltando no novo (cerca de 140 em todos os sites).

9. Como rodar e testar

docker compose up -d --build                                              # stack completa
FRONT_MODO=producao docker compose up -d --force-recreate --no-deps front # front como em produção
  • Sites: http://<chave>.localhost:3300, abrindo no Chrome. Chaves: hapvida, institucional, clinipam, landingpage, ccg, dashboards, minas, hapvida-porto-alegre, suavida, lp-hapvidacuidae, notredame.
  • Lista de todas as páginas, com o link novo e o original lado a lado: urls.html, na raiz do projeto.
  • Admin do Strapi: http://localhost:1337/admin.
  • Páginas que exercitam o dinâmico: hapvida/unidades, hapvida/canais-de-atendimento-presencial, hapvida/blog-da-saude, institucional/noticias, notredame/informacoes-regulatorias, notredame/duvidas-frequentes, hapvida/corretor, hapvida/ouvidoria.
  • Formulários: envie um formulário no site e confira em Content Manager → Envio de formulário.
